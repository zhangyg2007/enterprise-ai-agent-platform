# 第13课：从业务问题到可验收的 FDE 交付

学习目标：把前十二课的代码、模型、数据和运行证据组织成客户能审核、运维能接手的交付包。FDE（Forward Deployed Engineer）在本课程中的工作，是把业务问题转成明确边界、可复现演示和可追溯验收，并解释尚未解决的限制。

本课是文档与综合演练，不提供新的模型评估器或业务 API。先读[课程路线](../ROADMAP.md)、[第11课](11-enterprise-workflows.md)和[第12课](12-api-operations.md)。Ubuntu、真实 PostgreSQL、GPU 训练和四组模型对照的成绩必须来自实际运行；本地测试或填好模板不能替代这些证据。

## 1. 业务问题与交付边界

星桥工业服务是虚构企业。销售希望快速给出有依据的报价，人事希望员工安全查询和申请休假，采购希望根据库存与在途量生成补货草案。三个场景共同要求：数值可复算、权限可靠、经理独立审批、拒绝无业务效果、重试不重复生效。

| 场景 | 本课程实际边界 | 不能据此承诺 |
| --- | --- | --- |
| CRM | 100×3×(1−15%)=255.00，审批后生成派生报价回执 | 已同步客户真实 CRM 或完成销售订单 |
| HCM | 派生余额15天，批准3天后为12天 | 已修改真实HR系统、支持全部假期日历 |
| SCM | 30−(20−5+4)=11，批准后派生在途增至15 | 仓库已收货、供应商已收到采购订单 |
| M11 | M02只读冻结快照、独立业务账本、持久审批与回执 | 实时同步、回写M02或企业ERP |
| M12 | HTTP封装、服务器映射身份、单机运行和本地备份教学 | 企业SSO、公共TLS入口、高可用或生产SLA已交付 |

本课金额和数据都是教学值。客户提出“接入真实ERP”时，应记录变更、补充数据契约和验收条件，不能只把连接地址换成生产地址。

## 3. 分步综合练习

### 步骤一：用访谈缩小问题

打开模板01，分别扮演销售负责人、员工、采购经理。每个角色写一个输入、当前人工流程、错误后果和可观测成功条件。把“更智能”改成可测行为，例如“休假拒绝后余额不变，审批者必须与申请者不同”。

产出：至少3条需求编号、3条非目标和1条变更请求。先确认权限与副作用硬门槛，再协商质量/延迟目标；未经双方确认的阈值只能标“拟定”。

### 步骤二：冻结数据与身份契约

打开模板02，为报价金额、休假天数和库存单位填写类型、取值、来源与版本。记录M02导出时间、文件摘要以及M11账本标识。画清“源数据→冻结快照→派生账本”的关系，说明源系统之后的变化不会自动进入快照。

补全owner、独立manager、其他租户、运维四种访问主体。请求中的租户或角色不能覆盖服务器身份；thread ID只是定位符。审批者也不能任意修改已冻结输入。

产出：契约版本、权限表和至少4条负例，包括自批、跨用户、跨租户和资源版本冲突。

### 步骤三：先建追溯关系，再执行验收

打开模板03，逐行填写证据负责人和计划日期，现有证据填写准确位置及执行环境。M00、真实训练、真实PG等没有实际记录时，标“待执行”。为M11选择一个批准、一个拒绝、一个重试实验，为M12选择身份隔离和备份恢复实验，按对应教程运行。

一次实验至少记录：代码commit、Python/依赖、数据与配置摘要、执行身份、开始时间、步骤/命令出处、退出码、脱敏输出、判定人。负例还需要同环境正常请求成功作为对照；连接失败不能证明权限隔离成功。

产出：14行模块追溯表和按需求拆分的详细用例，保留失败与未执行项。

### 步骤四：设计并记录四组同集评估

按模板04冻结案例、标准答案、工具结果、语料权限及生成参数。A为基础模型，B为基础模型+RAG，C为同底座+adapter，D为同底座+adapter+RAG。先在validation选方案，冻结后才评估保留测试集。每题四组都保留输出和错误，不能删掉超时题。

已有M07评估器验证四字段分类和基础/adapter对照，M09验证检索与摘录；它们不能直接相加成四组端到端成绩。本课现提供统一采集器：先使用M09按固定租户、角色和日期冻结检索引用与业务快照，再依次用相同底座的base/adapter生成四组结果。采集器只收集输出及错误，不自动判定回答正确或引用适用；按模板由两位评审复核。冻结的业务事实由操作者提供，程序不会自行证明其来自真实数据库；第11课另有合成三案例串联，正式业务Agent仍待完成。未运行的质量格子填“待执行”，不填0。

先在M10应用环境做**合成管线**实验。以下命令在Ubuntu仓库根目录，输出必须是新路径：

```bash
python -m enterprise_ai.agent_cli --fixture --request '报价审批制度' --output reports/local/m13-input-01
python -m enterprise_ai.four_arm_freeze --seed data/samples/m13-four-arm-seed.json \
  --index reports/local/m13-input-01/index.json --state reports/local/m13-input-01/documents.sqlite \
  --fixture-encoder --output reports/local/m13-snapshot-01.json
python -m enterprise_ai.four_arm_eval --fixture --snapshot reports/local/m13-snapshot-01.json \
  --output reports/local/m13-comparison-01
python -m unittest tests.test_four_arm_eval tests.test_four_arm_snapshot -v
```

预期冻结三道题并保存M09租户、版本、角色/日期与来源摘要；四组各3条，总共12条，`kind=synthetic-fixture`。本示例沿用原M08权限，休假制度默认仅hr可见，因此employee题应保留空引用、RAG组记录`evidence_status=insufficient`，不能把员工提升为hr来获得证据；第11课的另一份合成实验显式调整了该示例制度的ACL，两者是不同实验数据。查看`records.json`与`report.json`，模拟模型只输出固定文本；完成仅表示采集流程执行，不代表模型质量。旧索引或错误embedding身份会拒绝冻结，角色无可见证据则保留空引用。事实快照是教学示例，不代表M02实时查询。

采集过程逐条写入`records.jsonl`并刷新；异常中断后可保留已完成行，没有`report.json`表示该轮不完整，不能按完整四组评分。当前不自动续跑：保留原目录，用新目录重新执行完整轮次。

真实实验分两环境：先在M09应用环境用已验收的真实索引/文档状态，执行相同`four_arm_freeze`命令，将`--fixture-encoder`换成`--embedding <已验证BGE本地路径>`，并使用经过授权审核的独立seed和输出路径；`--device cpu`或`--device cuda`必须与M09索引中的设备身份一致。再进入M07的Python 3.11/LLaMA-Factory训练环境，用同一冻结文件执行 `python -m enterprise_ai.four_arm_eval --snapshot <冻结文件> --release <M07已验收release目录> --output <不存在的报告目录>`。在受控私有目录操作，Linux先设置`umask 077`、Windows限制当前用户ACL；快照和原始回答可能包含敏感内容，Git忽略不等于访问控制。不导入未授权文本或真实私密数据到Git。程序顺序加载base及adapter，核对M07 release及资产，保留每题原始输出、摘要、错误和计时；失败计入分母，模型资产发生变化则整轮无效。事实是操作员自报的冻结值，正式评估需另留M02导出版本和身份核验。上述真实路径、GPU及质量评分尚未实测。

产出：四组输入清单、逐题记录表、指标定义、适用范围和限制；真实分数只在证据齐全后填写。

### 步骤五：估算成本并排练失败

用模板05代入教学工作量，分别算月度运行成本和一次性交付成本；用模板06排练三业务场景。先检查pending没有业务effect，再用独立经理批准；拒绝另开独立请求，不能反转已完成决定。按M11/M12手册模拟受控故障并从原线程恢复，核对回执和资源只变化一次。

失败时保留现场，区分“业务提交但图未保存”“资源冲突”“身份失败”。演示恢复到新目录或独立测试库，禁止覆盖原账本，也不要把换新幂等键当成重试。

产出：可复算预算、演示时间表、失败记录和恢复后的业务核对证据。

### 步骤六：交接与决定

用模板07列出资产、运行手册、访问责任、备份保留和已知缺口。由未参与实现的人仅依赖手册复述启动、停止、定位错误和恢复步骤；在授权环境实际演练后填写记录。

决定只能是“接受明确范围”“有条件接受，列条件”或“不接受”。未验证的GPU、PG、Ubuntu以及缺失的SSO/TLS生产集成必须显式列出。教学包文档齐全与客户生产验收是两个不同结论。

## 4. 参考答案与判定依据

先独立完成六步，再核对以下示例；示例是标准设计，不是客户运行结果。

1. 需求可以写“REQ-HCM-01：员工仅申请本人3天休假，独立经理拒绝时余额仍15，批准后派生余额12”。验收看事务回执和余额，而非模型说“已成功”。
2. CRM金额用十进制计算；HCM现阶段天数为严格正整数，1.5天需变更契约；SCM预留、现货、在途必须同单位。三个动作均需经理审批，不能自行增设自动审批阈值。
3. 源快照变了但旧草案没有重建，应说明数据时效限制；账本资源revision已改变则旧草案冲突，需重读并提交新草案。不能手改版本强行批准。
4. B−A表示在基础模型上的RAG变化，C−A表示无RAG时的微调变化，D−B表示有RAG时微调变化。只在同题、同精度、同工具快照和固定配置下解释；不预设D一定最佳。
5. “HTTP超时”不能说明业务失败。先查原请求与回执，已提交则恢复原线程；新键会代表新业务请求，可能再次扣假。拒绝和恢复成功都要有底层效果数证据。
6. 当前可以交付课程实现、空白模板及已有本地验证记录；不能签署“真实客户生产上线完成”。没有实际签字人和日期时保持空白，不替客户填同意。

## 5. 验收、常见故障与恢复

| 问题 | 修正方式 |
| --- | --- |
| 需求只有“回答准确” | 补具体样本、判定规则、分母、负责人及目标版本 |
| 只有截图没有运行上下文 | 补commit、配置/数据摘要、执行环境与原始输出位置 |
| 把M07分类分数写成FDE成功率 | 拆开模型协议、检索、授权、事务与端到端任务指标 |
| 演示依赖已污染的账本 | 新建独立实验并记录初始值；保留旧证据，不删除掩盖失败 |
| 模型或服务不可用 | 如实标记待执行；可展示已有录像但须注明日期/版本，不能说是现场成功 |
| 范围扩到生产SSO/ERP | 提变更，列依赖、工期、权限和新增验收；未实现前保留缺口 |

完成标准：七份模板均有可填写结构；需求有编号且能关联到用例；每个通过结论都能定位证据；未执行项有负责人和下一步；交接决定只覆盖已确认范围。独立review与实际verification分开记录。
